What this mock commits us to

Connected Portal+, landscape, 2160 × 1440 physical pixels, 180 dpi: the design uses a fixed 1920 × 1280 dp canvas. Light and dark themes use the color and sizing values in tokens.js. Roboto assets, bundled photo assets, Bebas and Flip font assets are included. The copy of the existing screensaver engine runs locally using sample photos.

Native implementation

After approval, create a new codex/ branch before any Android edits. Preserve the existing branch, working changes, preferences and configured widgets. This mock work has not edited Android source or installed an APK.

Use the existing settings registry for persistence, validation, visibility and side effects. Rich editors stay Activities reached through NavSpecs. Preserve sources, alarm days, connection forms, clock presets, MQTT TLS behavior, boot-app choices, source fallback, nine configured widget families, store catalog and installer daemon. Retired / automatic fields keep their current values.

Compose can reproduce these layouts using solid surfaces, shapes, bundled font files, vector icons and fixed dp dimensions. No live blur, iOS-only components, Google services, root or unsupported API is required. Kotlin services supply live data. Browser success results, currency rates, media sessions, calendars, rooms, albums and installed voice rows are clearly sample fixtures; they do not claim your device is configured that way.

Visual acceptance

The reference gallery records the approved visual state and popup patterns. Native completion requires a fresh APK build and relevant unit tests, installation only when authorized, then screenshots on this Portal+ compared with approved references at the same size, theme, font scale and fixture content. Check spacing, wrapping, typography, colors, corner radii, rows, popups and every reachable destination; fix differences before calling it matched. Browser verification establishes a reviewable design, not proof that native rendering already matches.

Behavior retained and explicit UX choices

The new shell groups screens into eight categories and uses consistent selection, number-entry, connection, confirmation and error patterns. The nine existing widget families are preserved and paged instead of silently discarded. Widget editing, favorite selection, app folder editing, recent-app actions, source forms, single Immich album selection, seven-day repeat pickers, all 14 screensaver style choices, five photo faces, six digital faces, story reader and voice memo states are available to review.

Apply the registry values and custom bindings from coverage.json rather than writing a new preferences model. Passwords never go into screenshots or artifacts. Generic selection popups are a proposed presentation change from existing segmented controls / dropdowns; their allowed values are preserved. Confirmation presentation and grouping are design proposals shown for approval. Any additional behavior discovered during native integration must be mapped and reviewed before a promise of final parity.

Existing interfaces

Browser, VLC, NewPipe, Home Assistant’s installed app, Material Files, F-Droid, Aurora Store, Breezy Weather, Jarvis, PortalHub, Portal Settings and Google Search retain their own screens. Music retains YouTube Music’s web interface; Calls retains the stock Portal calling bridge. Transistor radio and other catalog apps remain optional installations. Android permission, uninstall, widget provider and system settings interfaces are owned by Android / Portal firmware. The mock labels these boundaries; its explanatory panels are review annotations and are not native product UI.

Evidence limits

The app’s registry and all 49 manifest Activities were audited from this checkout. Read-only ADB verified hardware, installed apps, launchable components and nine widget families. Private current values, all third-party internal pages, and the authenticated installed schema were not exhaustively read. The source snapshot is tied to a commit and file hashes in the validation artifacts; installed version 1.64 / 58 alone does not prove byte-for-byte source equivalence.
